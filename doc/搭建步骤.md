# 搭建步骤

## 项目定位

面向程序员的多技术领域官方文档知识库 Agent。

LLM 根据用户任务自主选择检索、读取和报告工具，直到任务完成，并返回可引用的答案。

## 第一阶段：后端 TypeScript 化（当前阶段）

前端已使用 React + TypeScript。当前将 Express 后端从 JavaScript 迁移为 TypeScript，保持现有功能不变。

技术组合：

- Express + TypeScript
- `tsx`：开发运行
- Zod：请求和工具参数校验
- Vitest：单元测试
- `@types/node`、`@types/express`：类型声明


## 第一版已完成的工具

当前已完成的是固定 RAG 链路，工具尚未接入 Agent Loop：

- `ragSearch`（`services/rag/ragSearch.ts`）：Embedding、Chroma 召回、距离过滤、标题/路径加权、去重。
- `readAndChunkDocs`（`scripts/rag/readAndChunkDocs.ts`）：批量扫描、读取、清洗、切分 Markdown，生成 chunks。
- `AIsummary`（`services/rag/AIsummary.ts`）：接收检索片段，流式生成总结。

## 第二阶段：RAG 检索优化

当前 RAG V1 已有向量召回、距离阈值、标题/路径加权、文档去重，以及标题、段落和长度切分。

先完成基础优化：

 1. 将 `nResults`、命中阈值、过滤阈值和返回数量改为配置项。
2. 增加 `sources` 过滤，支持调用方显式指定来源或跨来源检索。
3. 增加来源识别：维护官方来源白名单，从用户问题中识别技术名称并转换为 `sources`；无法可靠识别时不传 `sources`，保持跨来源检索，避免漏召回。第一版只使用规则或词典匹配，不调用 LLM。
4. 前端展示知识库中的官方文档来源列表，允许用户选择一个或多个 `sources` 后再检索。
5. 提供来源列表接口（如 `GET /api/sources`），返回来源名称、技术领域、官方域名、文档数量和更新时间。
6. 返回标题、来源 URL、章节、`filePath` 和 chunk 标识。
7. 调整去重策略，同一文档保留最多 N 个相关 chunk。
8. 建立固定问题集，记录 Recall@K、MRR、引用准确率、延迟和 Token。

来源筛选的实现顺序：后端维护官方来源白名单 → `GET /api/sources` 返回可用来源 → 前端渲染多选列表 → `POST /api/search` 携带 `sources` → `ragSearch` / `retrieve` 按来源过滤。

### 已有优化项的职责归属

以下优化应按职责拆分，不全部归入 `retrieve`：

| 优化项 | 主要位置 | 说明 |
| --- | --- | --- |
| 筛选检索质量 | `retrieve` | 使用距离阈值和过滤阈值剔除低相关 chunk，属于召回结果筛选。 |
| 没有命中时不调用 LLM | `retrieve` + 调用方（当前为 `AIsummary`/路由） | `retrieve` 返回 `noContent` 或空结果；调用方根据该信号直接返回提示，不再请求 LLM。这是检索结果与生成阶段之间的流程控制。 |
| 去重与多样性 | `retrieve` | 当前按 `filePath` 只保留一个 chunk；后续应改为同一文档最多保留 N 个，并兼顾不同文档或章节的覆盖。 |
| 关键字加权 | `retrieve` | 在向量距离基础上，根据标题和文件路径中的关键词调整 `rankScore`，属于检索结果重排。 |
| RAG 参数集中管理 | `retrieve` 配置（后续可抽为共享配置模块） | 集中管理召回数量、阈值、返回数量和加权值，不改变检索流程本身。 |

因此，第二阶段基础优化的主文件是 `retrieve.ts`，但“无命中不调用 LLM”还需要同步检查 `routes/ai.ts` 或其上游调用逻辑。

再做质量增强：

- 混合检索：关键词检索 + 向量检索。
- rerank：重排 Top K 召回结果。
- 查询改写：处理中英文术语、技术缩写和同义词。
- 代码检索：代码问题单独检索代码 chunk。
- 上下文处理：合并相邻 chunk，按 Token 裁剪，保留章节层级。

RAG 优化分两次：Agent Loop 前完成基础优化和评测；Agent Loop 后根据任务日志继续优化。

## 第四阶段：Agent Loop

### LangGraph.js 引入时机

在第一阶段后端 TypeScript 化、第二阶段 RAG 基础优化、第三阶段两个 Agent 工具完成后，引入 LangGraph.js。

LangGraph.js 只负责 Agent 编排，不重写 `ragSearch` 或文档处理逻辑。它负责保存 `AgentState`、调用工具、把工具结果交回 LLM，并根据条件决定继续循环或结束任务。

### Agent 框架与 Harness 选型

当前项目采用 **LangGraph.js 作为 Agent 编排运行时，项目代码实现轻量 Harness，现有 TypeScript Service 提供工具业务逻辑**。

选择 LangGraph.js 的原因：

- 当前目标是单 Agent 的有状态工具循环，需要明确控制状态、节点、条件边、最大步数和终止原因。
- `ragSearch`、`readDocSection` 和 `createMarkdownReport` 都先作为普通 TypeScript 函数实现，接入图时只添加 Tool Adapter，不重写业务逻辑。
- 图运行过程可以流式输出模型消息、工具执行结果和自定义进度，便于转换为 Express SSE 事件。
- 模型调用、工具业务和图编排保持分离，后续更换模型供应商或将工具封装为 MCP 时，不需要重写 Agent 主流程。
- 后续可以按实际需求增加 checkpoint、恢复执行和人工确认，但第一版不提前引入这些复杂能力。

本项目不使用 LangChain 的高层 Agent API 代替核心循环。高层 Agent API 适合快速得到默认工具循环，但会隐藏一部分状态转换和终止判断，不利于本项目练习 Agent 编排，也不方便精确维护 `citations`、`reportPath`、连续失败次数和 SSE 业务事件。

这不表示完全排除 LangChain。LangGraph 与 LangChain 可以配合使用：按需采用 `@langchain/core` 的消息、工具和模型接口，减少适配代码；状态图、循环和运行边界仍由 LangGraph 显式管理。现有 OpenAI 兼容客户端也可以先封装在模型节点中，确认确有收益后再替换为 LangChain 模型适配器，避免一次性迁移。

框架职责：

```text
项目 Harness（完整的 Agent 运行与编排层）
├── 使用 LangGraph.js 实现状态图、节点、条件路由和 Agent Loop
├── 注册并调度模型与工具
├── 管理运行限制、超时、取消、错误、引用、日志和 SSE 事件
└── 调用 TypeScript Service
    └── ragSearch、readDocSection、createMarkdownReport 的业务实现
```

Harness 是项目中的完整 Agent 运行与编排层。它负责接收任务、初始化状态、驱动 Agent Loop、调度模型与工具，并统一处理安全边界、运行事件和结束结果。LangGraph.js 是 Harness 内部使用的编排引擎，提供状态图、节点、条件边和循环机制；它不等同于完整 Harness，也不负责替代工具中的业务逻辑。

推荐目录：

```text
server/src/agent/
├── state.ts
├── events.ts
├── errors.ts
├── tools/
│   ├── ragSearchTool.ts
│   ├── readDocSectionTool.ts
│   ├── createMarkdownReportTool.ts
│   └── toolRegistry.ts
├── nodes/
│   ├── callModel.ts
│   └── executeTools.ts
├── conditions/
│   └── chooseNextStep.ts
├── buildAgentGraph.ts
└── runAgent.ts
```

各层职责：

1. **模型层**：接收当前消息和可用工具，返回最终回答或结构化工具调用；不直接访问文件和数据库。
2. **工具层**：使用 Zod 校验参数，调用现有 Service，并把返回值或可恢复错误转换成统一工具结果。
3. **状态层**：保存任务、消息、引用、步数、连续失败次数、状态、最终回答和报告路径。
4. **运行控制层**：处理最大步数、工具超时、连续失败、请求取消和非法工具调用。
5. **事件层**：把状态变化转换成稳定的 SSE 事件，不让前端依赖 LangGraph 内部事件格式。
6. **观测层**：记录一次运行的步骤、工具名称、耗时、结果数量、Token 用量和终止原因，不记录 API Key 或完整敏感内容。

工具统一返回结构：

```ts
type AgentToolResult<TData> =
  | {
      success: true
      data: TData
    }
  | {
      success: false
      error: {
        code: string
        message: string
        retryable: boolean
      }
    }
```

第一版 SSE 事件：

- `status`：运行状态发生变化。
- `tool_started`：工具开始执行，包含工具名和当前步骤。
- `tool_completed`：工具执行成功，只发送前端需要的结果摘要。
- `tool_failed`：工具失败，包含稳定错误码和是否可重试。
- `citation`：发现可引用资料。
- `answer_delta`：最终回答的增量文本。
- `completed`：运行正常完成，包含引用和可选报告路径。
- `failed`：运行异常结束，包含终止原因。

Harness 的硬性运行边界：

- 第一版最大执行 6 步，后续根据任务日志调整。
- 连续 2 次工具失败后终止，避免重复调用无效工具。
- 为模型调用和每个工具设置超时。
- HTTP 请求断开或用户取消时，使用 `AbortSignal` 向模型和工具传播取消信号。
- 只允许调用注册表中的工具；工具参数必须通过 Zod 校验。
- `readDocSection` 只能读取文档根目录中的允许文件，并限制返回字符数或 Token 数。
- `createMarkdownReport` 只能写入报告目录，限制文件名、覆盖行为和内容大小。
- 达到限制时返回明确终止原因，不让模型继续自行循环。

引入顺序：

1. 先用普通函数完成 `ragSearch`、`readDocSection`、`createMarkdownReport`。
2. 定义三个工具的输入输出 Schema。
3. 定义 `AgentState`、统一工具结果、错误类型和 Harness 事件。
4. 为三个 Service 添加 Tool Adapter，并建立工具注册表。
5. 安装 LangGraph.js；按需引入 `@langchain/core`，创建单 Agent 图。
6. 配置模型节点、工具节点和条件边。
7. 增加最大步数、超时、连续失败和取消处理。
8. 增加 `/api/agent`，用 SSE 向前端发送工具调用和任务进度。
9. 使用固定任务集记录工具选择、引用准确率、步骤数、延迟、Token 和终止原因。

Agent Loop 跑通后，再根据真实任务日志继续做查询改写、复杂 rerank、代码检索和动态上下文裁剪等高级 RAG 优化。

```text
用户任务
  ↓
LLM 判断下一步
  ↓
调用 ragSearch
  ↓
证据不足？调用 readDocSection
  ↓
需要报告？调用 createMarkdownReport
  ↓
LLM 判断是否完成
  ├─ 未完成：携带工具结果进入下一轮
  └─ 已完成：输出带引用的答案
```

`AgentState`状态对象：

- `task`：用户任务
- `messages`：模型消息、工具调用和工具结果
- `citations`：来源引用
- `stepCount`：当前步数
- `status`：`running`、`completed`、`failed`
- `reportPath`：报告路径

终止条件：模型输出最终答案、达到最大步数（建议 5～8 步）、工具连续失败、无有效资料或用户取消。

第一版只实现单 Agent。使用 LangGraph.js 管理状态、工具调用、循环和终止条件；通过 SSE 把进度发送给前端。

Harness 完成标准：

- 用户只提交任务和可选来源，不再由前端决定先检索还是先总结。
- 模型只能调用注册的三个工具，所有参数均经过 Schema 校验。
- 检索结果中的引用以结构化状态保存，最终回答可以追溯到标题、章节、文件和来源 URL。
- 达到最大步数、连续失败、超时或取消时能够稳定结束，并向前端发送明确状态。
- SSE 可以区分工具进度、回答文本、引用和最终状态。
- 一次运行具有可追踪的步骤、耗时、Token 用量和终止原因，日志不包含密钥。
- Service 可以脱离 LangGraph 单独测试，Harness 不重复实现 RAG、文档读取或报告生成逻辑。

## 第五阶段：官方文档源扩展

不做任意全网抓取，采用官方来源白名单。可逐步加入：

- 前端：MDN、JavaScript、TypeScript、React、Vue、Vite、Next.js
- 后端：Node.js、Express、NestJS、PostgreSQL、Redis
- 工程化：Docker、Kubernetes、Git、GitHub Actions
- AI / Agent：OpenAI、LangChain、LangGraph、MCP

每个来源配置名称、官方域名、入口、同步方式、正文规则和更新策略。索引记录 URL、内容哈希和更新时间，支持跨来源检索与按来源过滤。

### 缺失来源的同步

增加 `syncOfficialDocs`：当用户查询的技术领域未收录时，从预配置的官方 Git 仓库同步 Markdown，再清洗、切分和增量索引。

限制仓库、分支、目录和 `.md` / `.mdx` 类型；首次接入新来源或大规模更新需要管理员确认。禁止执行模型生成的任意 Git URL。

## 第六阶段：MCP 封装

业务能力先实现为普通 TypeScript 函数，再提供 REST、LangGraph Tool 和 MCP 适配层。

一个 MCP Server 最终暴露：

- `ragSearch`：只读检索
- `readDocSection`：只读文档，限制根目录
- `createMarkdownReport`：写入报告，限制目录、文件名和覆盖行为

MCP 层只做 Schema 校验、调用 Service 和结果格式化，不重复实现业务逻辑。


## 第七阶段：前端页面优化（最后阶段）

前端在后端、RAG、Agent Loop、文档源和 MCP 稳定后再做完整优化。前期只保留输入框、来源选择、结果列表、总结内容和加载/错误状态，满足联调即可。

最后阶段集中处理：

- 页面布局、响应式适配和视觉层级
- 官方文档来源列表、多选过滤和来源状态
- Agent 工具调用、循环步骤和任务状态展示
- 流式回答、引用链接、代码高亮和 Markdown 下载
- 搜索历史、取消、重试和空状态
- 无障碍、性能和错误监控


## 推荐技术栈与完成标准

- 前端：React + TypeScript（后期需要 SSR 再考虑 Next.js）
- 后端：Express + TypeScript；稳定后再评估 NestJS
- Agent：LangGraph.js
- 工具协议：MCP TypeScript SDK
- 向量库：当前 Chroma，后期可迁移 PostgreSQL + pgvector
- 缓存与队列：Redis
- 部署：Docker Compose

完成后应能演示：用户提问 → Agent 检索 → 按需读原文 → 多轮判断 → 输出引用答案 → 生成 Markdown 报告，并可查看任务状态、耗时和 Token 用量。
